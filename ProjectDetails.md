## Building a Comprehensive WhatsApp Chatbot Platform with Next.js (Full Stack)

This project aims to build a fully integrated unofficial WhatsApp chatbot platform, relying entirely on **Next.js** as a comprehensive framework for both **Frontend** and **Backend**, with comprehensive **database management** and **WhatsApp operations**. This complex multi-stage system requires detailed planning and structured development using task management tools. By leveraging Next.js as a **unified full-stack solution**, we aim to streamline development, enhance developer experience, and ensure seamless integration between the client-side user interface and the server-side business logic, including direct database interactions and real-time WhatsApp communication.

---

### **Project Overview:**

Building an unofficial WhatsApp chatbot platform relying on Next.js as a single, integrated framework:

#### **The Single Application: Next.js Full Stack Platform**

- **Framework:** **Next.js 14+** with **TypeScript** and **App Router** (created using `npx create-next-app@latest`). The App Router introduces powerful server-centric capabilities, allowing for **server components** and **server actions** that execute directly on the server. This significantly reduces client-side JavaScript bundles and improves initial load times and overall performance. This architecture facilitates truly full-stack development within a single codebase, allowing developers to colocate frontend and backend logic for improved maintainability and data flow.

- **Styling:** **Tailwind CSS** with **shadcn/ui** component library. Tailwind CSS enables rapid UI development with a utility-first approach, ensuring a highly customizable and responsive design. It allows for direct styling within JSX, leading to faster iterations. Shadcn/ui provides pre-built, accessible, and highly customizable React components that seamlessly integrate with Tailwind. This accelerates UI development while maintaining a consistent and modern design language across the entire platform.

- **State Management:** **Zustand** for client state, and **TanStack Query** for server state management. Zustand offers a lightweight and flexible approach to managing global client-side state, making it ideal for UI-related states like navigation, modals, or form data. TanStack Query (also known as React Query) is crucial for managing server-side data. It handles complex data fetching scenarios, including caching, synchronization, background re-fetching, and error handling for data fetched via Next.js **API Routes** or **Server Actions**. This combination provides an excellent developer experience and highly optimized data fetching, reducing boilerplate code for data management.

- **Database:** **PostgreSQL** using **Prisma ORM** (for Code-First approach). PostgreSQL is a robust, open-source relational database known for its reliability, extensive feature set, and high performance for complex queries. Prisma acts as a next-generation ORM, providing **type-safe database access**, powerful **migrations**, and an intuitive API for interacting with the database. It simplifies complex CRUD (Create, Read, Update, Delete) operations and schema management, making database interactions more predictable and less error-prone.

- **Authentication:** **JWT-based authentication** with **Refresh Tokens** and **Role-based Authorization**, fully handled within Next.js API Routes/Server Actions. This secure authentication mechanism ensures that user sessions are managed efficiently. It uses short-lived **access tokens** (e.g., 15 minutes) for secure requests and longer-lived **refresh tokens** (e.g., 7 days) for seamless re-authentication without requiring re-login. All token validation and refresh logic will be processed on the server to prevent token exposure on the client side. Role-based authorization will be strictly enforced at the API route/server action level, controlling access to specific functionalities based on the user's assigned role (e.g., User, Admin, SuperAdmin).

- **WhatsApp:** **@whiskeysockets/baileys** library for WhatsApp Web API integration, used in Next.js Server Actions/API Routes. Baileys provides the core functionality for interacting with WhatsApp Web, enabling programmatic control over WhatsApp accounts. Integrating this into Next.js Server Actions/API Routes allows the application to handle real-time WhatsApp events and send messages from the secure server environment, abstracting the complex WebSocket management from the client and keeping sensitive Baileys logic server-side.

- **Purpose:** A **multi-tenant SaaS platform** providing comprehensive dashboards, in addition to managing core business logic and WhatsApp operations on the server side. The multi-tenant architecture will allow multiple organizations or individual users to operate their chatbots independently within the same platform instance. Each tenant will have their own isolated data and configurations, ensuring scalability, efficient resource utilization, and clear data separation for a robust Software-as-a-Service model.

### **Key Features (Integrated within Next.js):**

#### **User Management and Authentication:**

- **User registration/login with email verification:** A robust sign-up flow will require email verification to confirm user identity and prevent spam accounts. This will involve generating unique, time-limited verification tokens, securely sending emails via a service like **Nodemailer** (configured with **SendGrid** or a similar provider) triggered from a Next.js Server Action, and verifying these tokens upon user confirmation through a dedicated API route.
- **JWT authentication with Refresh Tokens and role-based authorization:** Users will receive a short-lived JWT (e.g., 15 minutes) upon successful login, which they will use as a bearer token to authenticate subsequent requests to protected API Routes/Server Actions. A longer-lived **Refresh Token** (e.g., 7 days) will be securely stored (e.g., in an HttpOnly cookie) to obtain new access tokens without requiring re-login. **Role-based authorization** will define granular permissions (e.g., 'User', 'Admin', 'SuperAdmin') for different API endpoints and UI components, ensuring users only access authorized features and data specific to their role.
- **Multi-factor authentication (MFA) for admin accounts using TOTP:** For enhanced security, administrator accounts will require MFA, typically implemented using Time-based One-Time Passwords (**TOTP**) generated by authenticator apps (e.g., Google Authenticator, Authy). This adds an extra layer of security, making it significantly harder for unauthorized users to gain access even if their primary credentials are compromised. Future considerations could include integrating with **FIDO2/WebAuthn** for even stronger second-factor authentication methods.

#### **Subscription and Billing Management:**

- **Subscription management with three tiers:** A flexible subscription model will be implemented, offering 'Free' (limited to **1 device** and **100 messages/month** for basic testing and evaluation), 'Pro' (allowing up to **5 devices** and **10,000 messages/month** for small to medium businesses), and 'Enterprise' (offering **unlimited devices** and messages for larger operations and custom requirements). Each tier will unlock different feature sets, usage limits, and support levels.
- **Stripe integration for subscription management:** **Stripe** will be the primary payment gateway, handling all subscription lifecycle events. Next.js **API Routes** will act as **webhook handlers** for Stripe events (e.g., `invoice.payment_succeeded`, `customer.subscription.updated`, `customer.subscription.deleted`), ensuring the platform's internal database is always synchronized with Stripe's records regarding subscription status, active plans, and payment information. This backend synchronization is critical for accurate service provisioning.
- **Usage Metering with real-time Quota Enforcement:** Every message sent or received through the platform will be metered and tracked against the user's subscription quota. This usage tracking will occur in real-time within Next.js Server Actions or dedicated background processes. The system will automatically enforce limits, preventing message sending if a user exceeds their allocated quota, with appropriate, timely notifications to the user about their usage and remaining quota.
- **Automated billing with prorated upgrades/downgrades:** The system will automatically handle recurring billing cycles through Stripe's subscription engine. For subscription changes (upgrades or downgrades), prorated billing will be implemented. This accurately calculates and adjusts charges based on the remaining time in the current billing cycle, ensuring fair and transparent invoicing for users as their needs evolve.
- **Invoice generation and email notifications:** Users will receive automated invoices for their subscriptions and usage directly from Stripe, or the platform can generate custom, branded PDF invoices. These invoices will be sent via email (integrated with SendGrid) at the end of each billing cycle, or upon any significant payment event (e.g., successful charge, refund), ensuring transparency and providing clear financial records.
- **Grace Period handling for failed payments:** In case of a failed payment, a configurable grace period will be initiated (e.g., 7-14 days), during which the user's service might be temporarily limited (e.g., reduced message quota, disabled new device connections) rather than immediately suspended. The system will attempt to retry payments during this period, and users will be proactively notified about the payment issue and potential service suspension.

#### **WhatsApp Integration (Server-Side within Next.js):**

- **WhatsApp device connection management with QR code generation and Session Persistence in the database:** When a user wishes to connect their WhatsApp account, a Next.js Server Action will initiate the process using Baileys to generate a dynamic **QR code**. This QR code data will be sent to the frontend for display. Once scanned by the user's phone, the secure Baileys **session data** will be captured and persisted in the **PostgreSQL database** via Prisma. This ensures the device remains connected and the session is durable even if the Next.js server restarts.
- **Multi-session support with session storage in PostgreSQL:** The platform will support connecting multiple WhatsApp devices for a single user or organization (e.g., different departments using different numbers). Each device's session data will be uniquely identified and stored in PostgreSQL, allowing the Next.js application to manage and interact with multiple WhatsApp instances concurrently and reliably.
- **Message operations: send/receive text, media, documents, templates:** The core functionality involves robust message handling. This includes sending and receiving standard text messages, various media types (images, videos, audio), documents (PDFs, spreadsheets, presentations), and pre-defined **message templates** for common responses or marketing campaigns. The system will correctly parse incoming message types and format outgoing messages.
- **Contact and group management with bulk operations:** Users will be able to manage their WhatsApp contacts and groups directly from the platform's interface. This will include functionalities like fetching contact lists, adding/removing contacts, creating/managing groups, and performing bulk operations such as sending a broadcast message to a large group of contacts or importing/exporting contact lists.
- **Media file handling with cloud storage integration (e.g., AWS S3 or similar via Server Actions):** All media files sent or received (images, videos, documents) will be handled efficiently to optimize database performance. Instead of storing them directly in the database, they will be uploaded to a secure cloud storage service like **AWS S3** using Next.js Server Actions. The database will only store a reference (URL) to the stored media, offloading heavy file storage and serving responsibilities to specialized services, improving scalability and reliability.
- **Connection status monitoring with Health Checks:** The connection status of each WhatsApp device will be continuously monitored. Automated **health checks** will periodically verify the active connection to WhatsApp's servers, and the status will be updated in real-time on the user dashboard. Automated notifications (e.g., email, in-app alerts) will be triggered for any disconnections or issues, prompting users to take action.
- **Rate Limiting to comply with WhatsApp's unofficial API limits:** Since `@whiskeysockets/baileys` interacts with WhatsApp's unofficial API, it's crucial to implement sophisticated **rate limiting mechanisms** to avoid being blocked or temporarily restricted. This will involve tracking outgoing message rates per device and per user, introducing smart delays or message queues if limits are approached, and implementing exponential backoff strategies for retries of failed messages.
- **Error handling and automatic reconnection logic:** The system will feature robust error handling for all WhatsApp operations, capturing and logging issues comprehensively. For intermittent connection drops or API errors, an automatic reconnection logic will be in place, attempting to re-establish the WhatsApp session gracefully without requiring manual user intervention, maximizing uptime for active chatbots.

#### **Chatbot Configuration:**

- **Chatbot configuration with template management and a drag-and-drop Flow Builder using React Flow:** Users will have a powerful and intuitive interface to configure their chatbots. This includes creating and managing reusable message templates (pre-defined responses with customizable placeholders) and a visual **drag-and-drop flow builder**, powered by **React Flow**. This intuitive builder will allow users to define complex conversational paths, conditional logic (e.g., "if keyword X is detected, then respond with Y and proceed to Z"), decision trees, and integrations for their chatbots without writing any code, making bot creation accessible to non-technical users.

#### **Analytics and Reporting:**

- **Message analytics with detailed reporting and export capabilities:** The platform will collect comprehensive data on message volume (sent/received), delivery rates, read receipts, and user interactions with chatbots. This data will be presented through detailed reports, allowing users to understand their chatbot's performance, identify popular conversational paths, and pinpoint areas for improvement. **Export capabilities** (e.g., CSV, PDF, JSON) will allow users to download their raw or aggregated data for external analysis or compliance.
- **Interactive analytics dashboard with charts using Chart.js or Recharts:** A dedicated analytics dashboard will provide interactive visualizations of key metrics. Using powerful charting libraries like **Chart.js** or **Recharts**, users can view trends over time, break down data by device, chatbot, message type, or time period. This interactive experience will enable users to gain actionable insights into their chatbot's effectiveness, user engagement, and overall messaging performance.

#### **Admin Controls:**

- **User management, platform performance monitoring:** **Super Admins** will have a dedicated dashboard to manage all users across the platform, including creating, updating, and deleting accounts, managing subscriptions, resetting passwords, and reviewing user activity logs. The platform monitoring section will display key system health metrics (e.g., server load, database connections, message processing queues, error rates, uptime of key services) to ensure smooth and efficient operation.
- **API Key Generation with scoped permissions and Rate Limiting:** For developers or integrators who wish to build custom solutions on top of the platform, a dedicated interface will allow generating API keys. These keys can be assigned specific scopes (e.g., read-only access to messages, permission to send messages only, chatbot configuration access) and their own rate limits, providing fine-grained control over external access to the platform's functionalities.
- **Comprehensive Logging:** The application will implement structured logging throughout all its layers using a production-ready logging library (e.g., **Pino.js** or **Winston** configured for server-side logging). Logs will capture critical events, errors, user actions, system activities, and performance metrics, all tagged with relevant context (e.g., user ID, correlation ID) to facilitate efficient debugging, auditing, and real-time operational monitoring.

#### **Real-time Updates:**

- **Real-time updates using WebSockets or Server-Sent Events (e.g., for connection status, new messages):** To provide a highly responsive and dynamic user experience, crucial information like WhatsApp device connection status changes, incoming messages, and live chat events will be pushed to the frontend in real-time. This will be achieved using **WebSockets** (e.g., by integrating a lightweight WebSocket server like `ws` or `socket.io` with a custom Next.js server setup) or **Server-Sent Events (SSE)**. This ensures users always see up-to-the-minute information without requiring constant page refreshes or polling.

#### **Security:**

- **Rate Limiting (using Redis for distributed scenarios):** Beyond WhatsApp-specific rate limiting, the platform will implement general **API rate limiting** to protect against abuse, brute-force attacks, and denial-of-service attempts. **Redis**, with its fast in-memory key-value store, is ideal for tracking request counts per IP address, per user, or per API key across multiple Next.js instances in a distributed deployment, ensuring consistent enforcement of limits and protecting backend resources.
- **Input Validation and Sanitization throughout the application:** This is a critical security measure applied at every entry point of data into the system. All user inputs and incoming data (from frontend forms, JSON payloads via API routes, or webhooks) will be strictly validated (e.g., using schema validation libraries like **Zod** or **Joi**) and **sanitized**. This includes preventing SQL injection (natively handled by Prisma ORM), Cross-Site Scripting (**XSS**) attacks, Cross-Site Request Forgery (**CSRF**) using anti-forgery tokens, and other common web vulnerabilities, ensuring data integrity and overall application security.
- **HTTPS enforcement:** All communication between clients and the Next.js server, and implicitly between internal Next.js API Routes/Server Actions, will be enforced over **HTTPS** (**HTTP Secure**). This encrypts data in transit, protecting against eavesdropping, data tampering, and man-in-the-middle attacks, which is fundamental for any secure web application.
- **Secure Credential Management:** All sensitive credentials (e.g., API keys, database connection strings) will be stored securely using environment variables or a secrets management service (e.g., AWS Secrets Manager, HashiCorp Vault) and never hardcoded in the codebase.
- **Content Security Policy (CSP):** Implement a robust CSP to mitigate XSS and data injection attacks by specifying allowed sources for various content types (scripts, styles, images, etc.).

### **Technical Architecture Requirements:**

1.  **Database Design (PostgreSQL with Prisma):**

    - `User` table: `id` (UUID, PK), `email` (unique, indexed), `password_hash` (string), `email_verified` (boolean, default false), `subscription_tier` (enum: 'FREE', 'PRO', 'ENTERPRISE', default 'FREE'), `created_at` (DateTime, default now()), `updated_at` (DateTime, updated on modify), `role` (enum: 'USER', 'ADMIN', 'SUPER_ADMIN', default 'USER'), `last_login` (DateTime, nullable), `mfa_secret` (string, nullable), `reset_password_token` (string, nullable), `email_verification_token` (string, nullable).
    - `WhatsAppDevice` table: `id` (UUID, PK), `user_id` (UUID, FK to `User`), `device_name` (string), `phone_number` (string, unique, indexed), `connection_status` (enum: 'CONNECTED', 'DISCONNECTED', 'PAIRING', 'FAILED', default 'DISCONNECTED'), `qr_code_data` (string, for temporary display of QR content), `session_data` (JSONB, for encrypted Baileys session data), `last_seen` (DateTime). Consider `device_token` for push notifications to notify users about connection drops.
    - `Chatbot` table: `id` (UUID, PK), `user_id` (UUID, FK to `User`), `name` (string), `configuration_json` (JSONB, for flow builder data, rules, triggers, customizable settings), `templates` (JSONB, array of reusable message template objects), `is_active` (boolean, default true), `created_at` (DateTime), `updated_at` (DateTime), `last_modified_by` (UUID, FK to `User`).
    - `Message` table: `id` (UUID, PK), `device_id` (UUID, FK to `WhatsAppDevice`), `chatbot_id` (UUID, FK to `Chatbot`, nullable), `from_number` (string), `to_number` (string), `message_type` (enum: 'TEXT', 'IMAGE', 'VIDEO', 'DOCUMENT', 'AUDIO'), `content` (TEXT, or URL for media content), `timestamp` (DateTime, indexed), `status` (enum: 'SENT', 'DELIVERED', 'READ', 'FAILED'), `media_url` (string, nullable), `caption` (string, nullable), `is_incoming` (boolean).
    - `ApiKey` table: `id` (UUID, PK), `user_id` (UUID, FK to `User`), `key_hash` (string, hashed API key), `permissions` (JSONB, array of strings like `['messages:send', 'analytics:read', 'devices:manage']`), `rate_limit` (integer, requests per minute), `usage_count` (integer, default 0), `expires_at` (DateTime, nullable), `created_at` (DateTime), `last_used` (DateTime, nullable).
    - `Subscription` table: `id` (UUID, PK), `user_id` (UUID, FK to `User`), `stripe_subscription_id` (string, unique Stripe ID), `plan_type` (enum: 'FREE', 'PRO', 'ENTERPRISE'), `status` (enum: 'ACTIVE', 'PAST_DUE', 'CANCELED', 'TRIALING', 'INCOMPLETE', default 'TRIALING'), `current_period_end` (DateTime), `created_at` (DateTime), `updated_at` (DateTime).
    - Usage tracking tables for billing and analytics (e.g., `MessageLog` with `id`, `device_id`, `user_id`, `message_count`, `date` (Date type for aggregation), `month`, `year`). This table will be populated via a cron job or background process to aggregate daily/monthly message counts per user/device against their subscription tier for billing and analytics.
    - These Models will be comprehensively defined in the **Prisma Schema** (`prisma/schema.prisma`), including relationships (one-to-many, one-to-one), and appropriate indexes for optimized query performance across frequently accessed columns.

2.  **Inter-Communication within Next.js:**

    - **Frontend components communicate exclusively with Next.js API Routes/Server Actions.** This follows the "single entry point" pattern, where the frontend never directly accesses the database or external services. All data fetching, mutations, and real-time interactions go through these secure server-side abstractions, ensuring a secure and well-controlled data flow, preventing exposure of sensitive logic or keys on the client.
    - WhatsApp events (received by Baileys inside Server Actions/API Routes) will trigger updates within the Next.js application's state, potentially using **WebSockets** for instant frontend updates. For instance, when a new message arrives or a device disconnects, a WebSocket event is emitted from the Next.js server, allowing the connected frontend dashboard to update in real-time without polling, providing a dynamic user experience.
    - Implement **Retry Logic** and **Dead Letter Queues** for failed webhook deliveries: If a WhatsApp event webhook (or any external webhook handled by a Server Action) fails to be processed by a Server Action (e.g., due to a temporary database issue, or external service outage), the system will retry processing it with an **exponential backoff** strategy. If repeated retries fail after a defined number of attempts, the event payload will be moved to a "dead letter queue" (e.g., a dedicated database table or a lightweight message queue like BullMQ within the Next.js app) for manual inspection and reprocessing, preventing data loss.
    - Use **Correlation IDs** for request tracing across the system: Every significant request (e.g., API call, webhook event, background job initiation) will be assigned a unique Correlation ID at its entry point. This ID will be automatically propagated through all layers of the Next.js application, from the initial frontend request to database operations, logging, and external service calls (like SendGrid or Stripe webhooks). This allows for easy tracing, debugging, and analysis of complex flows across logs and monitoring systems.

3.  **Authentication & Security (Managed by Next.js):**

    - **JWT Access Tokens (15-minute expiry) with Refresh Tokens (7-day expiry):** The short expiry for access tokens minimizes the window of opportunity for token compromise. The longer-lived refresh tokens, securely stored as HttpOnly cookies (to prevent client-side JavaScript access), allow for seamless re-authentication. The refresh token rotation strategy will invalidate old refresh tokens after a new one is issued, enhancing security.
    - **Role-based Access Control: User, Admin, SuperAdmin:** This will be implemented using a robust authorization middleware in Next.js (e.g., using the `middleware.ts` file for route protection or specific checks within **Server Actions**). Each API Route or Server Action will check the user's role extracted from the JWT. For instance, a "SuperAdmin" role might have unrestricted access to all admin functionalities, while an "Admin" can manage users within their organization, and a "User" can only manage their own devices and chatbots.
    - **API Key Authentication for external integrations with scoped permissions:** External integrations or partner applications will authenticate using uniquely generated API keys. These keys will be hashed and securely compared against stored hashes in the database. Each key will have explicit, granular permissions (e.g., `messages:send`, `analytics:read`, `devices:manage`) defined and enforced at the API level by the Next.js backend, allowing fine-tuned control over what external entities can access.
    - **Multi-factor authentication for admin accounts:** Beyond TOTP, considerations might include integrating with **FIDO2/WebAuthn** for passwordless or stronger second-factor authentication for highly sensitive administrative functions, providing increased resistance to phishing.
    - **Rate Limiting using Redis for distributed scenarios:** For preventing abuse and ensuring fair usage, a robust rate-limiting system will be implemented. **Redis**, with its fast in-memory key-value store, is ideal for tracking request counts per IP address, per user, or per API key across multiple Next.js instances in a distributed deployment environment, ensuring consistent enforcement of limits and protecting backend resources.
    - **Input Validation and Sanitization throughout the application:** This is a critical security measure applied at every entry point of data into the system. All user inputs and incoming data (from frontend forms, JSON payloads via API routes, or webhooks) will be strictly validated (e.g., using schema validation libraries like **Zod** or **Joi**) and **sanitized**. This includes preventing SQL injection (natively handled by Prisma ORM), Cross-Site Scripting (**XSS**) attacks, Cross-Site Request Forgery (**CSRF**) using anti-forgery tokens, and other common web vulnerabilities, ensuring data integrity and overall application security.
    - **HTTPS enforcement:** All communication between clients and the Next.js server, and implicitly between internal Next.js API Routes/Server Actions, will be enforced over **HTTPS** (**HTTP Secure**). This encrypts data in transit, protecting against eavesdropping, data tampering, and man-in-the-middle attacks, which is fundamental for any secure web application.

4.  **Subscription & Billing System (Managed by Next.js):**
    - **Stripe integration with webhook handling for subscription events:** The platform will fully integrate with **Stripe** for all billing operations. This includes using **Stripe Checkout** for initial subscription purchases, **Stripe Customer Portal** for user-managed billing (updating payment methods, changing plans), and crucially, robust Next.js API Routes acting as webhook endpoints to receive and process events from Stripe (e.g., `customer.subscription.created`, `invoice.payment_failed`, `customer.subscription.deleted`). These webhooks will ensure the platform's database is continuously synchronized with Stripe's billing state.
    - **Usage metering with real-time quota enforcement:** The system will continuously track messages sent/received per user (and potentially per device). This real-time data will be stored efficiently (e.g., in a dedicated usage log table in PostgreSQL, or using Redis counters for immediate checks). Next.js Server Actions handling message sending will perform these quota checks immediately, rejecting messages if limits are exceeded and notifying the user about their current usage and limitations.
